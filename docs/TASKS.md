## 2 逐任务验收细则

每个任务三条硬要求，缺一条不算完成：**产出文件存在**、**验收命令真跑过并留读数**、**至少一条反例被实测判红**（改坏实现 → 对应判据变红 → 改回）。第三条是防线：只有全绿的测试，无法证明它在测东西。

### K01 骨架与 profile
建**非 Electron 管理**的 `superagent` profile——这是 T10 的直接后果：`desktop` profile 被 Electron 独占，`dump-config` 直接报错，所有"生效配置"判据都跑不了。
验收要能判红的方式：把插件从 profile 的 bundle 清单里拿掉，计数必须掉到 0。只看到"计数 ≥1"不算过——那可能来自别的插件。

### K02 纯函数域：模型与 stage
`stage.ts` 是 7 行判定，**没有 I/O**，7 行表逐行可测。这是整个系统最值得写死的一段：它决定一条工单此刻该谁看。
反例：把第 3 行（`person/review`）的条件改成恒真，T05 必须至少一行红。若仍全绿，说明测试在测别的。

### K03 纯函数域：端口与引擎
`engine.ts` 是**唯一写者**（intake / ticket / report 三条命令路径），250 行里不允许出现 `await` 之外的宿主调用——它靠 `Repository` 接口拿事务，靠 `Executor` / `Gate` / `Outbox` 拿副作用。
反例：去掉 intake 的 `external_id` 去重，T01 必红。

### K04 存储与 schema 版本
6 张表，三条约束直接对应三条需求：`UNIQUE(external_id)`→R01、`UNIQUE(kind,key)`→R08、生成列 `active` + 索引→R18。
反例：库版本高于代码版本时**必须拒绝启动**（不是警告、不是降级）。这条最容易写成"打日志继续跑"，那等于 R18 没实现。

### K05 副作用队列
先 claim 再执行、成功才 settle；入队在事务内、执行在提交后。退避表见详设 §5.1。
反例就是 T08：`kill -9` 后重启，effect 被执行且**副作用只发生一次**。重放两次 = 幂等键写错。

### K06 组合根与 pass 循环
订阅 8 个宿主事件；pass 每 2 秒一次。判据是"停掉 pass 后 event 积压不消费"——反过来说，pass 挂掉必须表现为积压，而不是表现为丢事件。

### K07 执行器适配
建目录 + 建会话 + 投首条消息，受槽位约束；launch **一开始就占槽**（含准备阶段），人的消息可占额外一槽且优先（详设 §9.1 S4）。
反例：两 ticket 共用同一 session 或同一目录 → T06 必红。这是最容易"顺手复用一下"的地方。

### K08 kaa CLI 契约
只有一个出口，只读三样：退出码、stdout 的 JSON、事件是否落盘。**不 grep 人类可读文本**（文本随版本变）。
30 秒超时按瞬时失败进 effects 退避，不阻塞 pass。反例：桩进程挂起 30 秒，队列里必须出现一条退避记录且 pass 仍在跑。

### K09 触发源
`external_id = node:<id>:<revision>`——轮询同一叶子两次不得产生两个 event。轮询间隔与上限写死在配置里，不做无界遍历。
反例：同 revision 连轮询两次，`event` 表必须只 1 行。

### K10 出站与本地通道
outbox 保序 + 按 message id 幂等；v1 本地通道只做"回写 goal-tree + 控制台"（D5：`ds-bot` 要账号，账号是外部依赖）。
**回写走 kaa CLI，不直接 POST `goal-tree/lib/http.js` 的 `/node-action`**（S1 决定，ARCHITECTURE §3）。

### K11 worker 的 report 工具
worker 只有一个回写口：report 工具。三态 `ready` / `waiting` / `blocked` 驱动 stage。
反例：report 不落库时 T05 必红——用来证明 stage 判定真的依赖 report，而不是别的字段。

### K12 面板数据视图
不新建面板，复用 `plugin-console` 加 `person/*` 视图（详设 §9.1 S8）。只移植数据模型，不移植组件。
反例：删掉任一 stage 分支，视图快照必红。

### K13 验收测试 T01–T15
15 条对齐详设 §8。测试**不写成写被检代码的人写**（用户定的规矩）；主 agent 只验收：自己跑一遍、留读数、做一次破坏实验确认能判红。
预算测试（T13）是唯一"必须红"的测试：把某角色工具加满，它必须报错。

### K14 端到端与崩溃实测
manual 触发 → event → ticket → session → report → kaa 桩 → treeWrite 桩，全链路落库，一条命令可复跑。
外加一次真 `kill -9`：重启后在跑的 assignment 标 `interrupted`，effect 按序重放，外部动作不重复。

## 4 功能块（给人看的进度维度）

**为什么单列一节**：人打开面板想知道的是“哪个大块功能到什么程度、哪块卡住”，不是“第 14 个任务做完没”。任务表是执行维度，功能块是汇报维度，依赖层是诊断维度——三个维度，三份读数，别互相冒充。

**归组（14 个任务，无遗漏无重复，行数和 = 1699 实测）**：

| 功能块 | 任务 | 代码行 | 完成判据（一句话能否说出口） |
|---|---|---|---|
| 骨架与配置 | K01 | 0 | 插件能在 `superagent` profile 里被加载 |
| 判定与工单内核 | K02 K03 K04 K05 K11 | 931 | 一条 ticket 能走完 7 行 stage 判定，且 mandate 可读回 |
| 会话执行与恢复 | K06 K07 | 263 | `kill -9` 后重启能续跑，外部动作只发生一次 |
| 触发与出站 | K08 K09 K10 | 417 | 同 revision 只进一次；回写经 kaa 而非直接 POST |
| 观测与验收 | K12（+ K13 500 行测试、K14 编排） | 53 | 15 条测试全绿，且面板能看出每块状态 |

**块间依赖（跨块边只有 5 条）**：

```
骨架与配置 ──→ 判定与工单内核 ──→ 会话执行与恢复 ──┐
     └──────────────────────────→ 触发与出站 ──────┴─→ 观测与验收
```

**两个必须分开显示的读数**：

1. **投入量**：判定与工单内核占 **56%** 的 src（931/1,664）。按任务数算进度会骗人——5/14 看着 36%，实际一半多的活在这块。
2. **阻塞度**：骨架块 **0 行代码，却挡住全部 13 个任务**（它是依赖图里唯一入度为 0 的块）。所以“骨架 0% 且没动静”不是没事，是全线卡住。只显示投入量会把这种块画成“无感”。

**块完成的规矩**：块内叶子全 `done` **不等于**块完成。块必须有自己的集成判据（上表第四列），且 `done` 由人确认——否则会出现五条进度条 100%、系统跑不起来。K13/K14 干的就是这个。

**树形（2026-11-01 已重组）**：目标树现在是 `n1 → n9 → 5 个功能块 → 14 个任务`，**树深 4 层**。

| 树节点 | 功能块 | 子节点 |
|---|---|---|
| n10 | 骨架与配置 | n15 K01 |
| n11 | 判定与工单内核 | n16 K02 · n17 K04 · n19 K03 · n20 K05 · n26 K11 |
| n12 | 会话执行与恢复 | n24 K06 · n25 K07 |
| n13 | 触发与出站 | n18 K08 · n21 K09 · n22 K10 |
| n14 | 观测与验收 | n23 K12 · n27 K13 · n28 K14 |

**怎么重组成的**：`parentId` 只在创建时能设（`goal-tree/lib/tree.js:90`；`goal_node_update` 的 schema 只有 title/detail/depends_on），没有 reparent 接口，所以路径是「删 14 个 → 建 5 块 → 重建 14 个」。实测代价：33 次写操作、id 全换（K 编号不变，映射按上表）、语义零损失（14 个节点当时全是 pending 且无 result）。

**树读数（直接读 goal-tree 存储算，不是估；2026-11-01 21:xx 快照）**：节点 **41**、树深分布 `{1:1, 2:21, 3:5, 4:14}`、功能块 5、未了结叶子 **14**（n15–n28）、**依赖层仍是 8 层**（D0 n15 / D1 n16 n17 n18 / D2 n19 n20 n21 n22 n23 / D3 n24 / D4 n25 / D5 n26 / D6 n27 / D7 n28；用 D 不用 L，因为 `ARCHITECTURE.md` 的 L0–L4 是架构分层）、就绪只有 `n15 K01`。树形变了、依赖层与就绪集没变——这正是两个维度互不干扰的证据。

**n1 直接子节点（21 个）**：n2–n8 是已完成的前置任务（需求基线 / 能力盘点 / 需求文档 / 超额项 / 架构 / 详设 / 机检），n9 是落地实现，n29–n41 是后续的文档与机检任务（目录整理、文档设计、代码骨架、docs/ 收拢、判据复验、覆盖审计、读数自愈，均 `done`）。**别人数"深度 2 有几层"时别把这些直接子节点当成同一类**：其中只有 n9 一棵子树是开发任务，其余都是文档与验证任务。深度分布会随这类节点增减而变化，**所以它是快照不是不变量**；不变量是"5 个功能块 / 14 个任务 / 8 个依赖层 / 就绪只有 n15"。

## 5 开发流程（每个任务怎么开发）

**口径**：不统一走 TDD，也不每个任务先写一份设计。按「有没有纯函数边界」分三档——有边界的先写断言，没边界的先写判据；统一骨架都是**先红后绿**。

**不补设计文档**：接口 / 表 / 失败语义已在详设 §2、§3、§5 定死，§8 有 T01–T15。再写一份「逐任务设计」就是把同一份东西抄两遍，违反 §1.2.1 的单一定义点。开工前要做的是**契约对齐**（R→任务认领、`REQUIREMENTS.md` 里 18 条失效的 verify_cmd、Q1–Q4），不是新文档。

### 5.1 三档

| 档 | 判据（怎么认这一档） | 任务 | 红怎么造 |
|---|---|---|---|
| A 纯函数 / 纯视图 | 输入输出是纯数据，接口已在详设 §2 写死 | K02 K03 K12 | 断言可以先写：T05 七行 / T01 去重 / 快照 |
| B 有 I/O 与失败语义 | 必须真造故障才验得出来 | K04 K05 K08 K09 K10 K11 | 坏夹具先写：库版本改高、`kill -9`、桩挂 30 秒、同 id 发两次 |
| C 配置 / 组合根 / 编排 | 没有可断言的纯函数 | K01 K06 K07 K14 | 判据先行：删 bundle 行、停 pass、`kill -9` 全链路 |
| 测试本身 | 交付物就是测试 | K13 | 15 条按详设 §8 逐条落地 |

**K07 的例外**：`sessionController` 的真实参数只读到自述、没实跑过，开工先做 ≤30 分钟 spike 定参数，再进 B 档流程。

### 5.3 测试专家的边界

- **谁写**：K02–K13 的 `.ts` 测试与 K14 的 `verify.sh` 一律交 `subagent`（空白上下文）写，写实现的人不写测它的测试。K01 / K06 的判据是一行命令，不算测试代码，与实现同轮出现。
- **派的时候必须自带**：详设 §2 签名、§8 的 T 编号、坏夹具要求、真实文件路径、只许改 `tests/`、跑一次把读数贴回、不许写「建议你……」。
- **代价已知**：派一个 40 行的测试曾花 92 步 / 6.59M token，贵在它反复猜格式。所以一次只派一个任务包，不派整个 K13 的 500 行；prompt 里塞满上下文不是浪费，是省步数。
- **主 agent 只做验收**：① 自己跑一遍专家的命令并留读数；② 改坏一条判据，确认对应夹具**变红**（改坏后仍红 = 夹具在测别的东西，打回）。

### 5.4 收口三件套

每个任务完成只认三样，缺一不算完成：**产出文件存在**、**验收命令真跑过并留读数**、**至少一条反例被实测判红**。三样读数写进目标树节点的 `result`，没有读数的「做完了」不算记录。
